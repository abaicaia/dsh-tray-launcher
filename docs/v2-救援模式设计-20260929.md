# 救援模式设计 v2（2026-09-29）—— 目标：DSH 的大部分故障都能救回来

> 前置：`v2-设计讨论记录.md`（2026-09-02 初版共识）、`v1.1-开发复盘与经验库.md`（架构与坑）。
> 本文件 = 在初版基础上，**做完社区调研 + 本机源码验证后**的完整设计。
> 结论先行：**救援模式的价值不在"再造一个安全模式"（社区有做），而在"DSH 完全起不来时，谁是唯一还能动的东西"——那个东西只能是启动器。**

---

## 1. 先摸清"DSH 会怎么坏"（故障谱系 → 救援手段）

设计救援模式的第一步不是写代码，是**把故障列全**。按"DSH 还能不能跑"分两大类：

### A 类：DSH 能跑，但**界面/某功能**坏了
| 故障 | 典型症状 | 救援手段 |
|---|---|---|
| Web 界面打不开 / 卡在 "Failed to load plugins" | 页面白屏、插件 pending | **TUI 顶替**（`dsh --profile <tui>`）或安全模式 |
| 某个插件坏（客户端半报错） | 界面红条、功能缺失 | 禁用该插件 → 重启 |
| 单个插件导致 boot 后功能异常 | 日志 `did not activate` | 同上 |
| 补丁丢失（升级后） | 设置页空白、兼容补丁失效 | `apply-patches.mjs` 重打 |
| 隧道/手机通道断 | 手机连不上 | `tunnel-switch` 检查/重启 |
| 会话格式不兼容 | 会话打不开 | 会话迁移链体检（**先备份再修**） |

### B 类：DSH **完全起不来**（← 这才是救援模式的真正战场）
| 故障 | 典型症状 | 救援手段 |
|---|---|---|
| **patch/overlay 里有一行指向未安装的包** | `ERR_MODULE_NOT_FOUND`，**进程直接退出** | **① 启动器改/回滚 patch ② 快照还原** |
| 核心损坏 / 版本错 | node 起不来、import 失败 | 回滚 `runtime.pre-*`（升级工具已有） |
| profile 配置损坏（package.json / cordis.yml） | profile 加载失败 | 备份还原 |
| junction 田断链 | 模块找不到 | 修复链接（升级工具已有） |
| 端口占用 / 残留进程 | EADDRINUSE | 进程清理（启动器已有） |
| 磁盘满 / 内存耗尽 | 启动即死 | 诊断报告（提示人工介入） |

> **关键认知（来自社区 #3473，原文很精准）**：
> "a plugin that cannot load is bad; **a harness that will not start is worse, because it removes every tool you would otherwise use to diagnose it**."
> —— 插件坏只是坏一个功能；**DSH 起不来会把你所有自诊断的工具一起拿走**。

## 2. 社区现状：别人做了什么（我们**不该重造**什么）

### 2.1 官方：**没有**一键安全模式（已核实源码）
- 社区请求 [#5076](https://github.com/deepseek-ai/deepseek-harness/discussions/5076)（2026-08-30，用户原话："dsh 有没有像手机的安全模式，直接关闭所有用户插件启动，方便用户卸载有问题的插件？"）→ **与我们这次的诉求一字不差**
- 同一讨论里 @argszero 查了 0.1.2-alpha.1 源码，结论：**全树没有 `--safe-mode` / `--no-user-plugins` 之类的 flag**
- 官方另有 `dsh doctor` 提案 [#1719](https://github.com/deepseek-ai/deepseek-harness/discussions/1719)（**68 条评论、仍 open**）→ 说明"官方诊断命令"这事讨论了三个月还没落地

### 2.2 ★ 三条**不依赖 UI** 的禁用路径（@argszero 的源码考古，本机已验证）
| 路径 | 做法 | 适用 |
|---|---|---|
| **A 单插件禁用** | `cordis.patch.yml` 里 `- id: <条目id>` + `disabled: true`；`assertEntriesLoaded` 把 disabled 视为**唯一合法的无 fiber 状态** → 即使该模块解析失败也不阻塞启动 | 已知是哪个插件坏 |
| **B 条件禁用 = 一行实现"手动安全模式"** ⭐ | `disabled: !!js process.env.DSH_SAFE_MODE === "1"` → 平时正常启动；出问题 `DSH_SAFE_MODE=1 dsh --profile <名>` 即以禁用态进入 | **最接近"安全模式"的现有形态** |
| C 独立 recovery profile / 临时 `DSH_HOME` | 社区 @liyangbing 建议：**先快照问题 profile**，记录版本/插件清单/第一条错误，再在隔离环境验证 | 需要"边修边试" |

**✅ 本机 0.1.7 实测（我做了，不是照抄社区）**：
- `cordis-plugin-include\lib\index.js`：`const JsExpr = new yaml.Type("tag:yaml.org,2002:js", {...})`
- `cordis-plugin-loader\lib\index.js`：注释 "Recursively replace YAML `!!js` expression nodes with evaluated values"
- → **`!!js` 条件表达式在本机核心可用**，路径 B 成立
- 旁证：我们今天禁用/启用 `browser-playwright` 与 `tool-browser` 走的就是路径 A，DSH 启动正常、`plugin_health` 干净

### 2.3 ⚠️ 必须先知道的"尖角"（#3473）
- 在 `cordis.patch.yml` 里加一行 `name: '@example/not-installed'` → **boot 期 `ERR_MODULE_NOT_FOUND`，进程退出**（不是"一行失效"，是**整个 harness 起不来**）
- 后果链：Web UI 没了 → 不能在 UI 里修；"检查运行中树"的工具也没用 → **因为没有运行中的树**；**唯一后路 = 手改 YAML 或恢复备份**
- 作者两条经验（**直接决定我们的设计**）：
  1. **"检查必须发生在写入之前，不是之后"** → 他自己的工具现在会**验证每个插入的包在 profile 里存在，否则拒绝写入**
  2. **"每次写之前快照，同样重要"** → 他 brick 了自己的测试 harness **两次**，都是靠备份救回来的

### 2.4 现成工具（**能借就借，别重造**）
| 工具 | 定位 | 与我们的关系 |
|---|---|---|
| [**dsh-safe-tui**](https://dsh.deepseek404.com/detail.php?id=aorucshiea%2Fdsh-safe-tui) | **安全模式/修复专用 TUI**：不加载用户插件、不加载 Web、只允许官方系统预设（minimal/standard/code/cordis），**用于主界面打不开时修复系统** | **界面层救援**——但它本身也要靠 DSH 启动，属 A 类故障 |
| [dsh-plugin-doctor](https://github.com/deepseek-ai/deepseek-harness/discussions/1693) | 插件健康检查（RFC #1629 的实际实现） | **诊断层可借**（我们已有 compat-preflight / check-client-inject） |
| dsh-overlay-check | overlay 校验（MIT、纯 Node、零依赖） | **预防层可借**（正是 #3473 说的"写前检查"） |
| [社区手册 plugin-recovery](https://sandbaseai.github.io/deepseek-harness-handbook/plugin-recovery.html) | profile 快照 / 逐层隔离 / 无破坏诊断 / 失败回滚 / 验证门槛 | **流程可借**（非官方，按本机实际情况取用） |

## 3. 我们的定位：**唯一在"DSH 完全起不来"时还能动的东西**

`dsh-safe-tui` 等方案再优雅，**都得先把 DSH 跑起来**才能加载——**B 类故障里它们一个都用不上**。

**而 `DshLauncher.exe` 是独立 C# 进程**：DSH 起不来、Web 打不开、甚至 node 都启动失败时，**它照样能读写文件、改配置、起停进程、开日志**。

> **所以救援模式的定位不是"再做一个安全模式"，而是"把启动器变成 DSH 的急救包"**：平时是托盘，出事时是唯一入口。

## 4. 设计方案（五层，层层递进）

### L0 预防层 —— 让故障**别发生**（最高性价比）
1. **写前校验**（借鉴 #3473 + dsh-overlay-check）：
   - 任何"往 `cordis.patch.yml` / `package.json` 写入插件条目"的动作，**写入前必须验证该包在 profile 里可解析**；
   - 解析不了 → **拒绝写入**（而不是写完等 boot 崩）。
   - 现状：我们已有 `compat-preflight.mjs`（插件↔核心兼容）与 `check-client-inject.mjs`（客户端幽灵依赖），**但缺"patch 行指向的包是否存在"这一条** → **补一个 `check-patch-rows.mjs` 或并入现有检查器**。
2. **每次写前快照**：`cordis.patch.yml` / `package.json` / `cordis.yml` 写入前自动备份（含时间戳），保留最近 N 份。

### L1 诊断层 —— 出事时**先留证据，再动手**
- 启动器一键"**收集现场**"（只读，不修）→ 生成 `rescue-brief.md`：
  - 核心版本 / profile 列表 / **用户插件清单**（从 package.json + patch 汇总）
  - **第一条启动错误**（stderr 首条 + 尾部 30 行）
  - junction 田状态（链接数/断链数）
  - 端口占用、残留进程
  - 最近改动过的文件（按 mtime）
- 借鉴升级工具：**VERDICT 式结论文件**、**探针化**（V01–V05 那套只读检查）
- 铁律（@liyangbing）：**诊断和修复必须分开**；**不要一上来就删整个 home 或重装**（那会毁掉定位问题所需的 manifest/lockfile/patch/凭据/sessions）

### L2 安全模式 —— 让 DSH **能起来**
**首选：路径 B（`!!js` 条件禁用，已验证可用）**
- 给"用户插件"在 patch 里加一行条件禁用：`disabled: !!js process.env.DSH_SAFE_MODE === "1"`
- 启动器进救援 = 以 `DSH_SAFE_MODE=1` 启动实例（**不需要改任何文件**，退出即恢复）
- **⚠️ 必须明确"哪些能跳、哪些不能跳"**（@liyangbing 的关键建议）：
  - **可跳过**：用户装的社区插件（皮肤、市场、面板、搜索……）
  - **不可跳过**：Host / 身份 / 传输类（如 `dsh-tunnel-switch`、`qq-mode-console`、认证相关）——跳过它们会让"救援实例"本身不可用或行为诡异
- **备选：路径 C（独立 recovery profile / 临时 `DSH_HOME`）** —— 需要"边改边试"时用

**兜底：界面层交给 `dsh-safe-tui`** —— 若只是 Web 打不开，直接起 TUI 预设（我们不必自己做 TUI）

### L3 修复层 —— 安全模式下**具体怎么修**
按"最小动作、可回滚"排序：
1. **禁用/卸载问题插件**：优先用 `dsh plugin --profile <p> remove <pkg>`（**别手写 patch**——#3473 的教训就是手写一行能搞死 boot）
2. **恢复配置备份**：patch / package.json 回滚到快照
3. **回滚核心**：复用升级工具的 `-Action Rollback`（`runtime.pre-*` 秒级换回）
4. **修 junction 田**：复用升级工具的补链逻辑（只补不删）
5. **重打补丁**：`apply-patches.mjs`
6. **会话格式体检**：逐会话只读检查 → 先备份再修（借鉴 Obsidian 插件那个"会话格式修复"按钮的粒度）

### L4 退出与验证 —— **修完要能证明修好了**
- 退出救援：清 `DSH_SAFE_MODE` → 起正常 3080 → 跑**验收**（复用升级工具的验收项：端口 / dump-config / 插件激活数 / 农场断链 / 补丁 marker）
- **必须验证**（@liyangbing 的四条）：插件清单完整、配置正确、**凭据边界未破**、**一个已知 Session 仍可读**
- 产出 `rescue-report-<时间戳>.md`（主会话复盘用）——沿用 8/29 那次的实际做法（`logs\对话记录-DeepSeek排查20260829.md`）

## 5. 关键设计决策（避坑清单）

| # | 决策 | 理由 |
|---|---|---|
| 1 | **救援 ≠ 重装** | 重装会毁掉 manifest/lockfile/patch/凭据/sessions，反而让人无法定位问题（#5076 里 @liyangbing 明确反对"重装解决"） |
| 2 | **绝不靠"手写 patch"做救援** | 手写一行指向未安装的包 = **整个 harness 起不来**（#3473）；优先用 `dsh plugin` CLI |
| 3 | **进救援必须停主实例** | 避免抢配置 / 抢 sessions / 抢记忆库（初版共识，仍然成立） |
| 4 | **救援中 3s Timer 必须感知 mode** | 否则自动拉起逻辑会和互斥锁打架（初版 §三.2，最容易漏的耦合点） |
| 5 | **救援实例用独立端口（3090）** | 与主实例隔离；且总内存不翻倍（主实例已停） |
| 6 | **必须显示 degraded 状态** | 让用户知道"现在哪些插件被跳过了"（@liyangbing 建议）；不能静默降级 |
| 7 | **救援自己也崩要有出路** | 3090 起不来 → 报 stderr 尾部 + **任何时候都能"退出救援回 normal"**，不锁死用户（初版 §三.5） |
| 8 | **开机自启要收敛到启动器** | 现状是 Chrome PWA 自启（绕过启动器）→ 救援互斥拦不住（初版 §三.1，仍未决） |
| 9 | **不做通用插件框架** | 老板的防屎山铁律：只留小而明确的 seam（状态机 / 命令表 / 探针） |

## 8. 目录结构与代码质量（2026-09-29 重构后）

### 目录分类
启动器根目录一度有 **30 个散文件**（源码 / 脚本 / 图标 / 文档 / 产物全混在一起）。整理后：

| 位置 | 内容 |
|---|---|
| 根 | `DshLauncher.exe`（产物，桌面快捷方式指向）、`build.cmd`（双击入口）、`ask-xiaod.cmd/.ps1`（**代码依赖 `ExeDir`，必须留根**）、`README.md`、`.gitignore`、运行期 pid |
| `src\` | 7 个 .cs（`DshLauncher` / `LauncherCore` / `LauncherConfig` / `LauncherLog` / `ModeGate` / `RescueMode` / `AssemblyInfo`） |
| `scripts\` | `build-launcher.ps1` / `package.ps1` |
| `assets\` | `dsh-launcher.ico` / `pwa-logo.ico` |
| `docs\` | 8 篇设计/经验/发布文档 |
| `tests\` | `test-fallback*.ps1` + 说明 |
| `backups\` | exe 历史备份 |
| （原有） | `logs\` `release\` `package-src\` `github-repo\` |
